# 開発運用と段階ゲート

このリポジトリは、共通基盤を完成させてから機能実装に進みます。この運用の導入時点は **G0（環境再現）の整備段階**です。
Issue の登録、作業ブランチの作成、コードの存在だけでは、後段の作業を開始できません。
着手可否は、統合先 `develop` の `.github/core-gate.json`、依存 Issue の完了条件、証跡で判断します。
共通運用と API コアの完了判定は `IA-Bgroup/BGroup-api` が正本です。
WBS No.17 は **API コア → Web 共通部品 → No.17 全体の完了確認** の順に進めます。No.18 の画面機能はその後に開始します。
API の G3 完了と API 側の `featureDevelopmentAllowed: true` は Web 共通部品へ進むための条件であり、画面機能の解禁や No.17 全体の完了を意味しません。

## 仕様の基準

先生承認済みの ER 図を DB 設計の基準とします。G1 は承認を取り直す段階ではなく、承認版と実装の一致を検証する段階です。
ローカルモック、試作用データ、過去の提案は、そのまま正式仕様にはしません。

承認 ER、WBS、画面仕様などは、チーム管理の資料 ID・版 ID・項目 ID で参照します。
公開ファイル、Issue、PR には、資料リンク、個人名、日程、非公開資料の内容を転記しません。
GitHub 上の担当者・レビュアーはアカウント名で指定します。

## ゲートと完了条件

| 段階                             | 対象                                                                    | 通過に必要な証拠                                                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G0：環境再現                     | 実行環境、依存関係、ローカル DB、起動手順、基本 CI                      | 新しい作業環境で依存関係を導入し、空のローカル DB に migration を適用できる。API の起動・health・ready・全チェックの実行結果を残す                            |
| G1：承認 ER と DB の一致         | 承認版の識別、テーブル・列・型・キー・制約・参照関係、seed と migration | 承認版との対応を確認し、空 DB からの構築、制約・参照関係の異常系、必要な初期データを検証する。差分と対応結果を管理 ID で記録する                              |
| G2：共通契約                     | API の入出力・エラー・ページング、認証、権限、業務状態・状態遷移        | 採用する契約と実装が一致する。未認証・権限不足・不正な状態遷移などの拒否動作をテストし、機能側が独自解釈しなくてよい状態にする                                |
| G3：API コア結合と別メンバー再現 | DB と共通 API の結合、起動・初期化・検証手順、API コアの完了判定        | 必須の API コア Issue と PR が統合済みで、別メンバーが手順を再現する。結合確認、CI 成功、阻害事項なしを証跡付きで確認し、専用 PR で完了を記録する             |
| FEATURE：機能開発                | WBS No.18 に沿った機能単位の実装と画面接続                              | API コアと Web 共通部品を含む No.17 全体の完了後、各 Issue の依存関係を満たした作業だけ開始する。契約確認 → API・テスト → 画面接続 → 結合確認の順で完了させる |

各ゲートの詳細な成果物は、対応する WBS 項目と Issue に定義します。技術方式や業務ルールの未確定事項を、CI が通ったという理由で確定扱いにしません。
後段の資料整理や Issue の登録は先に行えますが、後段の実装、機能画面の接続、契約を変える作業は開始しません。
同じ段階でも、依存関係がある作業は先行成果物の完了を待ちます。

## WBS No.17 と画面機能の開始条件

1. **No.17 の前提を整える（G0）**。開発環境、依存関係、ローカル DB、起動手順、CI を再現できるようにします。WBS No.34 は出展端末の環境整備であり、G0 の完了条件には使用しません。
2. **API コアを完成させる（G1〜G3）**。承認済み ER と DB を照合し、共通 API、認証・権限、入力・エラー、状態などの契約を実装・検証します。別メンバーが API コアを再現した証跡まで確認します。
3. **Web 共通部品を完成させる（No.17 の後半）**。API の G3 完了と API 側の `featureDevelopmentAllowed: true` を確認してから、確定した契約を使う API クライアント、共通エラー表示、認証状態の扱い、入力・遷移など、採用した共通部品を実装・確認します。Web の `foundation` / `G3` として扱い、画面ごとの業務機能を混ぜません。
4. **No.17 全体を完了にする**。API と Web の対象 Issue・PR・テスト・再現記録を確認し、共通部品を利用できる状態であることを別の確認者が確認します。API 側の G3 や Issue の close だけで代替しません。
5. **No.18 の画面機能を開始する**。Web 側の `.github/web-gate.json` に共通部品の証跡と `sharedComponentsComplete: true`、`featureDevelopmentAllowed: true` が記録され、No.17 全体の完了条件と各機能の先行 Issue が揃ったことを確認します。ゲート更新 PR が統合された後の別 PR から機能実装を進めます。

No.21 の全体試験や No.27 の全機能結合試験は、画面機能の実装後を含む工程です。これらの全体完了を G3 の前提にして、No.18 と循環させてはいけません。
API コアに必要なテストは No.17 の受入条件として先に実行し、画面機能後の試験と区別します。
Web の Issue・PR テンプレートや運用手順などの保守は、`foundation` / `G0` として API の進捗と独立して進められます。この扱いを共通部品や画面機能の前倒しに使用しません。

## ゲートの通過手順

1. ゲート担当は、必須 Issue、対応 PR、対象 commit、検証結果、残課題を集めます。
2. 確認者は、完了条件を証跡と照合します。G3 では作者以外による環境再現を含めます。
3. ゲート変更だけを扱う PR で、通過対象と根拠の管理 ID を記載します。通常の機能実装を混在させません。
4. 必須チェック、作者以外の承認、指摘の解決後に `develop` へ統合し、次段階の Issue の着手条件を確認します。

ゲート判定は統合先の状態を使います。機能 PR が自分の差分でゲートを解除しても、着手条件を満たしたことにはなりません。
API 側では `.github/core-gate.json` の `gates.G0` から `gates.G3` までと `featureDevelopmentAllowed` を確認します。
Web 共通部品の完了は、Web の信頼する base 上の `.github/web-gate.json` の `sharedComponentsComplete`、`featureDevelopmentAllowed`、`evidence` で確認します。
No.18 の機能開発には、両リポジトリの条件に加えて、Web 共通部品を含む No.17 全体と各機能の依存 Issue が完了していることも必要です。
API のゲートは証跡付きの単独 PR で一段ずつ通過し、後段だけを先に完了扱いにしません。Web のゲート更新も共通部品の証跡を伴う単独 PR とします。
PR が自分の差分で解禁フラグを変更して、その PR 内の機能実装を許可することはできません。
ゲートの記録と実際の証跡が矛盾した場合は、後段の作業を保留し、修正 Issue で原因と再開条件を記録します。

## Issue の登録と状態

すべての作業は所定の Issue フォームに登録し、次の項目を揃えます。

- 変更区分、対象ゲート、WBS の資料 ID・版 ID・項目 ID
- 目的、成果物、対象範囲、仕様参照
- 依存 Issue、着手条件、阻害事項
- 合否を判断できる完了条件
- DB・API・権限・状態への影響と、必要な移行・復旧方法
- 検証手順、期待結果、証跡の保存先 ID
- GitHub アカウントによる担当者と別の確認者

| 状態       | 条件                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 未着手     | 登録済みだが、着手条件の確認前                                             |
| 着手可能   | 必須項目、担当・確認者、先行 Issue、対象ゲートが揃っている                 |
| 作業中     | 着手可能であることを確認して実装中                                         |
| レビュー中 | PR と検証結果が揃い、確認を依頼している                                    |
| 保留       | 依存未完了、仕様の未確定、検証失敗などがあり、理由と再開条件を記録している |
| 完了       | 必要な PR が統合され、完了条件・証跡・統合 commit を確認済み               |

状態は Issue の実態を表します。ラベルやボードの列だけを変えても、着手条件や完了条件は省略できません。
関連 Issue は `Closes #番号`、先行する依存 Issue は各行 `Depends on #番号` の形式で記載し、同じリポジトリの番号を使います。
依存がなければ `None` の行と理由を記載します。PR の依存一覧は関連 Issue の一覧と一致させます。
フォーム送信時の必須入力は、記載内容の正しさまでは保証しません。API 経由の登録や本文編集も含め、着手前とレビュー時に内容を確認します。

## PR の必須項目とマージ条件

PR テンプレートの見出しは、自動検査と人による確認の共通形式です。削除・名称変更をしないでください。
関連 Issue、変更区分、対象ゲート、WBS 参照、目的と変更内容、依存関係、契約への影響、検証結果、証跡を記載します。
説明コメント、空欄、理由のない「なし」だけでは記入完了としません。

通常の統合先は `develop` です。`main` はリリース範囲を確認した `develop` → `main` の PR で更新します。
マージは次の条件をすべて満たした後に行います。

- 関連 Issue の完了条件を満たし、依存関係とゲートを確認している
- 必須チェックが最新の変更で成功している
- 作者以外の確認者が承認し、未解決の指摘がない
- 必要な仕様・migration・テスト・手順が変更に追従している
- 検証環境、対象 commit、実際の結果、証跡が確認できる

レビュー後の変更は影響に応じて再確認します。未実行の検証を成功として記録しません。
CI の成功だけでは、業務仕様との一致や別メンバーの再現確認を代替できません。
`develop` 向け PR のマージ後は、Issue が自動 close されるとは限らないため、完了条件を確認して手動で閉じます。

## DB・API・状態の変更管理

承認版や共通契約を変える作業は、通常の機能実装に混ぜず、先に `change` Issue で扱います。

1. 変更前後、必要な理由、参照資料 ID、影響する Issue と利用側を記載します。
2. migration、既存データ、互換性、権限、状態遷移、テスト、移行・復旧への影響を確認します。
3. 必要な関係者確認を記録し、変更の前提が揃うまで影響する後続 Issue を保留します。承認済み ER そのものを変更する場合は、学校側で必要な手順に従います。
4. 仕様と実装を更新し、既存の適用済み migration は書き換えず、新しい migration を追加します。
5. 影響範囲を再検証し、対応 PR と証跡を記録して後続作業を再開します。

既存の承認版を実装するだけの作業に、先生の再承認を要求しません。
依存先が利用している契約を破る場合は、関連する完了判定も見直し、影響が解消するまで利用側の完了を主張しません。

## 自動検査と運用の役割

Issue・PR の形式、CI、ゲートの状態は自動検査の対象です。仕様判断、証跡の妥当性、再現確認はレビューで確認します。
この文書に規則を書いただけでは GitHub の保護設定が有効になったことにはなりません。

API の `main` と `develop` では、初期の必須条件を `Quality checks` の成功と作者以外 1 名の承認とします。
管理者は PR 必須、承認、必須チェック、force push・削除の制限が実際に有効か確認し、設定結果を記録します。
`PR policy` は、基盤導入 PR の統合によって信頼する base に workflow と検査処理が入った後、別の activation Issue で動作とチェック名を確認してから必須条件に追加します。
基盤導入前の base に存在しないチェックを、導入 PR 自体で既に強制済みとは説明しません。activation Issue が完了するまでは、`PR policy` の必須化は未完了として扱います。

現構成の `BGroup-web` は Private / Organization Free のため、サーバー側のブランチ保護を利用できません。
Web の workflow にチェックを導入しても、それだけで直接 push、未承認のマージ、失敗したチェックを無視したマージを必ず阻止できるわけではありません。
Web では同じ Issue・PR・レビュー手順を守り、マージ担当者が最新のチェック結果と No.17・各機能の依存条件を確認します。API のサーバー側保護と Web の運用上の確認を区別して報告します。
公開範囲や契約プランを変える場合は別の判断として扱い、保護機能のために公開化しません。

初期設定・障害対応で保護設定を変えた場合は、その理由と復旧確認を追跡できる形で記録します。

## 例外時の扱い

失敗したチェックや未完了ゲートを無視してマージしません。まず阻害事項を Issue に記録し、対象段階の修正として扱います。
機能解禁前の `bug` は既存基盤の修正に限定します。`foundation`、`change`、`bug` という区分名で機能実装の前倒しを正当化しません。
緊急性があっても Issue・PR・証跡・別メンバーの確認を残し、ゲート変更や権限変更を機能 PR に混ぜません。

## main への昇格とチェックの再実行

通常の作業は `develop` に取り込みます。`main` 向け PR は同一リポジトリの最新 `develop` からだけ作成できます。
別ブランチ・fork・古い commit からの直接 PR は検査で拒否します。昇格では `develop` で確認済みのコードとゲートをまとめて反映するため、通常作業の「ゲート更新は単独 PR」の制約を再適用しません。
Issue・PR 必須項目、依存完了、証跡、作者以外のレビューは昇格でも必要です。
`develop` の保護とレビューを維持することが、この昇格運用の前提です。

`workflow_dispatch` は手動監査用です。そこで成功しても PR の必須チェックが更新されるとは限りません。
依存 Issue の状態を更新した後は、その PR の既存 `PR policy` を Re-run するか、PR 本文を編集して再検査してください。

パス制限は作業範囲の境界を検査します。許可された `src/index.ts` や共通部品へ業務機能を詰め込むような意味上の違反まで判定するものではありません。
担当者以外がコード・仕様・証跡を確認するレビューを必須とします。
